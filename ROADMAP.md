# TimeTrack — план развития

## Правила работы

- Сначала новая вкладка баланса отпусков, затем безопасность и стабилизация. Критические риски не откладывать до публичного развёртывания.
- Сохранять Go/Fiber, MySQL/sqlc, Vue 3/Pinia и текущие соглашения проекта.
- Маленькие независимые изменения; не переписывать рабочие модули, не добавлять зависимости без необходимости.
- Не писать новые автоматизированные тесты; существующие не удалять. Проверять сборку, форматирование, статические проверки и вручную ключевые сценарии. Не заявлять об успешной проверке, если её не выполняли.
- Перед изменениями изучать актуальное состояние репозитория; не перезаписывать чужие незакоммиченные изменения. Не менять production-данные, секреты или настройки развёртывания без согласования.
- После каждой задачи сообщать изменённые файлы, результат проверок, ограничения и оставшиеся риски. Обновлять чек-лист только после выполнения.

## 1. Баланс отпусков сотрудников (текущая задача)

- [x] Выбор года (по умолчанию текущий), поиск по ФИО, сортировка по имени и остатку.
- [x] Таблица: сотрудник, годовая норма, утверждено дней, ожидает согласования, остаток. При наличии проверенного источника подразделений — фильтр по отделу. Не придумывать поле отдела: в backend `authservice.UserResponse` его нет; изучить существующие справочники frontend.
- [x] Сводка: число сотрудников, утверждённые дни, ожидающие дни, сумма остатков, рассчитанные из того же набора данных; явно определить, что сводка относится ко всем загруженным сотрудникам выбранного года.
- [x] Показ сотрудников без заявок; заполнение нулями при наличии корректной нормы. Не скрывать ошибки загрузки за нулевыми значениями.
- [x] Состояния загрузки, ошибки с повтором, пустой список, адаптация к узкому экрану. Цветовая индикация малого/нулевого остатка в существующем стиле.
- [x] Перерасход — отдельное поле/индикатор `excess`, не отрицательное значение существующего `free`.

### Ручная приёмка

- [ ] Админ видит три вкладки; обычный сотрудник — только разрешённые; прямой API-запрос без `.all` отклоняется, без сессии тоже.

- [ ] При смене года и фильтров обновляются нужные данные; возвращение на заявки работает; ошибки/403 не оставляют старые данные; проверить мобильный вид.
- [ ] Сравнить выборочные значения с индивидуальным `/stats`; проверить сборку backend/frontend штатными командами, gofmt, sqlc generation. Если среда/SSO/БД недоступны, зафиксировать непроверенное, не выдавать за пройденное.

### Реализация и проверки (16.11.2026)

- Документы отсутствовали в корнях обоих репозиториев; использованы приложенные версии из Downloads. Этот файл — рабочая копия ROADMAP.md в корне frontend. CODEX_PROMPT.md изучен, не изменён.
- Реализованы backend API и административная вкладка. Новые автоматизированные тесты не добавлялись; существующие не удалялись. Этапы 2–8 не изменялись.
- Контракт: `GET /vacation/balance/:year` (frontend: `/apitime/vacation/balance/:year`) возвращает массив `{userId, surname, name, patronymic, total, used, pending, free, excess}`. `patronymic` может быть `null`. Существующая `response.Success` возвращает данные непосредственно, без дополнительного объекта-обёртки. Неверный год — 400, отсутствие сессии — 401, отказ middleware — 403, ошибки источников/настройки — 500 с существующим полем `error`.
- Включены все пользователи из `authService.GetAllUsers`: в текущем проекте нет определённой кадровой политики по статусам/ролям. Список может включать неактивные или технические учётные записи; их исключение требует бизнес-правила. Отсутствующие заявки дают нулевые суммы только при корректной норме.
- Сохранены `start_date`, `total_days`, `affects_balance`, учёт будущих утверждённых отпусков. Ожидающие заявки не уменьшают остаток; перерасход возвращается отдельно. Норма читается один раз, список пользователей — один раз, суммы всех пользователей — одним SQL-запросом.
- Отсутствующая, NULL, нечисловая или отрицательная норма блокирует административный баланс с понятной ошибкой. Старый `/stats` сохраняет прежний контракт: отсутствие строки даёт нулевую статистику; NULL/нечисловое значение — fallback 30. Это намеренное различие нового административного API, чтобы не показывать ложный баланс.
- Реальный источник отделов: `/apiref/ref/employees/internal`, связь по `user_id`/`id`. Локальный `reference.api.js` помечен skip-worktree и содержит mock-fallback; сохранён без наших изменений. Для баланса добавлен узкий сервис `internalEmployees.api.js` без fallback. При ошибке справочника баланс остаётся доступен, показывается сообщение об отключённом фильтре. При отсутствии отделов в ответе фильтр не показывается.
- Сводка рассчитана по всему загруженному набору выбранного года, без поиска/фильтра отдела. Низкий остаток: 1–7 дней, нулевой — отдельный цвет. Сортировка доступна и в мобильном виде.
- Store очищает данные при смене пользователя/прав и размонтировании вкладки, игнорирует устаревшие ответы. Ошибки, включая 403, не оставляют старый баланс. Service Worker использует NetworkOnly для нового API; успешный backend-ответ содержит Cache-Control: no-store.
- Выполнено успешно: `sqlc generate` по существующему sqlc.yaml, `gofmt`, `go build ./...`, `go vet ./...`, `npm run build`, `git diff --check` в обоих репозиториях. Для Go использован `GOCACHE=/private/tmp/timetrack-go-cache`, поскольку системный кеш недоступен в sandbox. Frontend-сборка предупреждает о чанках больше 500 kB; оптимизация вне текущего этапа. Сгенерированный Service Worker содержит правило NetworkOnly перед общим правилом API.
- Live-серверы, curl, БД и ручные проверки через SSO не запускались. Пункты ручной приёмки выше остаются неподтверждёнными; проверить права, примеры 14/7 и 32 дней, исключённые типы/статусы, будущие и переходящие отпуска, смену года/прав, возврат на заявки, ошибки источников, мобильный вид и сравнение с `/stats`.
