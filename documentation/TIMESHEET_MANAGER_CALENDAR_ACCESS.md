# Выбор сотрудников руководителем и требование подтверждения

## Состояние реализации

Реализованы оба изменения: выбор доступных сотрудников на календаре и освобождение собственного табеля назначенного руководителя от обязательного подтверждения.

По уточнению пользователя для освобождения достаточно действующего назначения в `department_managers`. Наличие разрешения не является дополнительным условием освобождения. Для доступа к подчинённым и действий руководителя по-прежнему нужны и разрешение, и назначение.

## Источник списка

Используется существующий `GET /v1/timesheets/:year/:month`. Новый endpoint не потребовался. Для руководителя обработчик List использует `Policy.Members → DepartmentScopeResolver.Members`: проверяет разрешение сессии, получает все действующие назначения по user_id, строит множество строк department и сопоставляет актуальные записи APIREF. Компания не участвует; собственный userId исключается из подчинённых. Сам resolver возвращает множество ID, frontend дополнительно устраняет дубликаты по userId.

Для руководителя options строится исключительно из серверных строк и отдельной записи текущего пользователя. Глобальный usersAll не определяет доступность сотрудников. Он по-прежнему может использоваться существующими механизмами приложения для вспомогательных метаданных выбранного пользователя; fallback к глобальному списку кандидатов при ошибке запрещён. Администратор с calendar.all:read сохраняет прежний список.

Список обновляется вместе с initialFetch, включая открытие собственного календаря, смену месяца/сотрудника и повторную загрузку. До загрузки и при сбое scoped-список очищен. Есть отдельное действие «Мой календарь»; очистка выбора у руководителя возвращает к себе. При отсутствии назначений или разрешений backend не выдаёт scoped-список. Для статистики без доступных гендерных метаданных используется уже полученная защищённая statistics из той же строки API.

Прямое обращение к календарю через URL по-прежнему проверяет `Policy.Require("read", false)` на backend. Выбор не меняет права на редактирование, историю или согласование; work-only, обязательная причина и защита системных записей остаются в существующих слоях.

## Необходимость подтверждения

Backend вычисляет `requiresApproval` по текущим назначениям владельца табеля. Для одного месяца используется существующий ListDepartmentManagersByUser, для списка — один ListDepartmentManagers с множеством userId, без запросов для каждой строки. Есть хотя бы одна строка — false, нет строк — true. Ошибка чтения БД не превращается в освобождение: возвращается ошибка API. Признак добавлен в ответы месяца, списка и подтверждения/снятия, включая current при 409.

В timesheet_months ничего не меняется ради назначения: pending не заменяется approved, не создаются фиктивные авторы, даты или история. После снятия одного из нескольких назначений освобождение остаётся, после последнего requiresApproval снова true; реальный сохранённый статус не сбрасывается. Изменение права при сохранённом назначении само по себе не отменяет освобождение — это уточнённое правило пользователя.

Календарь и таблица показывают «Подтверждение не требуется» при false. Общий административный список и статистика часов по-прежнему содержат этих сотрудников; фильтры статусов согласования, их счётчики и знаменатель прогресса включают только требующие подтверждения табели. Сохранённые автор и дата последнего подтверждения остаются в таблице. При отсутствии нового поля у старого backend применяется прежнее требование подтверждения.

Проверки Policy.Authorize, canApprove, expectedRevision, запрет руководительского самоподтверждения и все административные действия не изменены. Администратор сохраняет возможность отдельно подтвердить или снять подтверждение освобождённого табеля согласно прежним правам. Само назначение не выдаёт новых прав доступа.

Backend понадобился, чтобы выдавать единый признак календарю и административному списку, а не скрывать pending только у текущего пользователя. Новые внешние endpoints, таблицы, миграции и конфигурация не потребовались. Обновление backend необходимо для появления нового поведения; исторические данные не переписываются.

## Проверки

Исполнены `go build ./...`, `go vet ./...`, `npm run build` и `git diff --check` обоих проектов: успешно; Vite предупреждает о размере chunks. Для go vet использован GOCACHE в /tmp из-за ограничения доступа к системному кэшу. Dev-сервер, живые API/БД-проверки и новые автоматизированные тесты не запускались.

Проверено только по исходникам / ручные сценарии:

1. Обычный сотрудник — новый селектор не появляется; собственный календарь сохраняется.
2. Назначенный руководитель одного отдела — backend выдаёт только участников отдела.
3. Несколько отделов — resolver объединяет все назначения, frontend не ограничивает первым.
4. Повторы ID в ответе — один вариант в селекторе. Неоднозначные записи справочника по-прежнему исключаются resolver, а не исправляются frontend.
5. Одинаковые имена отделов разных компаний — действующая department-only логика сохранена.
6. Только разрешение без назначения — backend отказывает, fallback отсутствует.
7. Назначение без разрешения — не открывает доступ.
8. Удаление одного назначения — после обновления список включает только оставшиеся отделы.
9. Удаление всех назначений/разрешения — после обновления scoped-список не остаётся доступным.
10. «Мой календарь» и очистка руководительского выбора возвращают к текущему пользователю.
11. Прямой недоступный userId — backend-проверка календаря не изменена.
12. Просмотр подчинённого не снимает запреты системных/кадровых записей; обработчики редактирования не менялись.
13. Собственный табель назначенного руководителя — requiresApproval=false в API и «Подтверждение не требуется» в календаре; фиктивного approved нет. Проверить назначения с выданным и отозванным разрешением: освобождение зависит только от назначения.
14. Подтверждение подчинённого — существующие canApprove, ревизии и обработка конфликтов не менялись.
15. Календарь и /report получают один и тот же requiresApproval: освобождённый сотрудник виден в общем списке, отсутствует в очереди pending/needs_review и не увеличивает знаменатель прогресса. После удаления последнего назначения проверить возврат в соответствующую очередь без изменения исторического статуса.
16. Административный выбор использует прежний usersAll и calendar.all:read; сбой scoped API не подменяет административные права.
