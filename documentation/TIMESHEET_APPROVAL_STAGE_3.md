# Подтверждение табелей — frontend, этап 3

Реализована интеграция существующей страницы `/report` с backend этапа 2. Backend, SQL, миграции, расчёты времени и интерфейс редактирования дней не изменены. Этап 4 не начат.

## Изменения

- `/report` и пункт навигации открыты для прежнего `calendar.all:read` и `department.manager:manage` через существующий meta.departmentManagerAccess. Права обычного календаря и карточки сотрудника не расширялись.
- Список и вся месячная статистика загружаются одним `GET /timesheets/:year/:month` через прежний timeTrackApi (`/apitime`, прокси в `/v1`). Список usersAll не используется как источник строк и не фильтруется для выдачи доступа руководителю.
- После review восстановлена прежняя глобальная инициализация usersAll для всех ролей: справочник нужен существующим разделам. ControlsCalendar в режиме report не инициирует дополнительную загрузку. Страница руководителя не использует usersAll для строк табеля и не загружает полный APIREF или статистику произвольных сотрудников. Источником доступных табелей остаётся только GET timesheets.
- Администратору сохранены прежние числовые столбцы, условные офис/удалёнка, раскраска нормы, ФИО со ссылкой на карточку, переход к календарю выбранного месяца, группировка/фильтр отделов и печать. Метки отделов берутся из того же APIREF исключительно в административной ветке и не определяют доступ. После review запрос меток ограничен 5 секундами, без mock-fallback; при ошибке таблица остаётся доступной без фильтра отделов.
- Добавлены статусы pending/approved/needs_review, автор и дата последнего подтверждения, фильтр по статусу, четыре сводных показателя и прогресс. Сводка учитывает выбранный отдел до фильтра статуса, поэтому выбор «Подтверждён» не превращает общий прогресс в 100%.
- Строки без доступной статистики показывают прочерки, а не нулевые часы. Статус подтверждения такой строки остаётся видимым.
- Действия отображаются только по строгому `canApprove === true` от backend. Не делается самостоятельного вывода о праве согласования из роли, чтения, редактирования или совпадения своего ID.
- POST approve/unapprove передаёт только expectedRevision актуальной строки и ждёт успешного ответа. Во время операции повторный клик блокируется. После ответа список обновляется. Оптимистического присвоения approved нет.
- При 409 список перезагружается, выводится уведомление о необходимости проверки изменившегося табеля. Сообщение «данные обновлены» показывается только при успешной перезагрузке. При ошибке загрузки строки очищаются и доступна кнопка повтора; fallback на полный список сотрудников отсутствует.
- Счётчик загрузок и ключ месяца защищают от старых ответов при быстром переключении месяцев. Операция всегда использует месяц и ревизию, захваченные при нажатии.
- Для timesheets добавлено исключение NetworkOnly из существующего PWA API-кеша: статус/сотрудники/право canApprove не восстанавливаются из офлайн-кеша другого запроса. Прежнее исключение vacation/balance сохранено.

Повторно использованы ButtonUI, SelectUI, Badge, ControlsCalendar, LoaderTitle, уведомления и переменные оформления. В печати скрыты кнопки решений, новые столбцы компактны. Форм редактирования времени руководителем нет; его строки не ведут на административную карточку/существующий редактор. Административные ссылки сохранены.

## Ограничения контракта

Backend отдаёт approvedBy как ID, без отдельного ФИО автора. Имя разрешается из текущего пользователя и доступных строк; у администратора также из уже загруженного usersAll. Если профиль недоступен, отображается сам ID автора; ради его имени руководитель не загружает глобальный список.

Backend не отдаёт названия отделов в scoped-списке. Руководителю показан плоский разрешённый список и фильтр статусов; административный фильтр отделов сохранён. Новые поля backend для этого не добавлялись.

После needs_review отображается именно последнее подтверждение, а не утверждение актуальной ревизии. При явном снятии backend очищает автора/дату. Подтверждение всего месяца без статистики по неизвестному полу допустимо backend; UI не вводит новое бизнес-ограничение.

- `src/router/index.js` — доступ и существующая навигация для руководителя.

- `src/constants/timesheet.constants.js` — подписи/виды статусов.
- `src/stores/report.js` — backend-список, статистика, проверенные capabilities, ревизия, операции и ошибки.
- `src/pages/report/Index.vue` — сводка и совместные фильтры.
- `src/components/Report/ReportTable.vue` — прежняя таблица с новыми колонками и действиями.
- `src/components/ControlsCalendar.vue` — отключение глобальной загрузки в report.
- `src/stores/user.js` — после review прежняя обязательная глобальная инициализация восстановлена.
- `vite.config.js` — NetworkOnly для timesheets в PWA.
- `documentation/TIMESHEET_APPROVAL_STAGE_3.md` — этот отчёт.

## Проверки

Выполнены production-сборка `npm run build` и `git diff --check`. В package.json нет отдельных lint/typecheck-команд. Новых тестов нет. Dev-сервер, живые запросы и браузерная проверка не запускались. Сборка выдаёт предупреждение о крупных chunks; конфигурация разделения bundle в этот этап не изменялась.

Сценарии ниже требуют ручного выполнения с backend этапа 2 и реальными сессиями; они не объявляются пройденными.

| Сценарий | Ожидаемый результат |
|---|---|
| Обычный сотрудник | Прежний собственный календарь и medical-дни работают. `/report` и пункт «Табель» не доступны без нужного права. |
| Руководитель без calendar.all:read, прямой вход в `/report` | Видит пункт меню и только строки GET timesheets. Глобальная инициализация users/timetrack сохранена для других разделов. Сам report не использует её результат для строк; нет полного APIREF или отдельных statistics-запросов страницы табеля. |
| Руководитель без назначения / сбой APIREF | Backend 403/503, видимая ошибка, нет чужих/старых строк и fallback. |
| Подбор userId / изменение client state | Решения проверяются backend; frontend-строки и скрытые кнопки не заменяют авторизацию. |
| Администратор | Все прежние колонки, группировка по отделам, фильтр, карточка и календарь выбранного месяца сохранены. Числа совпадают с прежними backend-расчётами. |
| read-only администратор | Видит таблицу, но у строк canApprove=false нет действий подтверждения. |
| Руководитель и свой табель | Кнопки нет, если backend не вернул собственную строку/canApprove. Отдельное административное разрешение учитывается только через backend-флаг. |
| Подтверждение pending / needs_review | Один POST approve с expectedRevision. До ответа нет успеха/смены статуса; после обновлены статус, автор, дата и сводка. |
| Снять подтверждение | POST unapprove с expectedRevision, после ответа pending и очищенная мета. |
| Конкурентная правка после загрузки | 409, загрузка актуального списка, предупреждение, без автоматического повторного approve. |
| Перезагрузка после 409 не удалась | Нет ложного сообщения об обновлённых данных; видима ошибка загрузки, устаревшее действие недоступно. |
| Повторный быстрый клик | Пока запрос выполняется, повторная операция для того же сотрудника/месяца не отправляется. |
| Быстрая смена месяцев / смена во время POST | Старые ответы не заменяют новый месяц; POST относится к исходному месяцу, его ответ не присваивается строкам другого месяца. |
| Фильтр отдела + статуса | Условия совместимы, сводка по выбранному отделу не теряет остальные статусы; исчезнувший отдел сбрасывается на «Все». |
| Неизвестный пол / недоступный профиль автора | Числа прочерками; автор показан по ID без глобальной загрузки. |
| Сбой API или отключённая сеть в установленной PWA | Нет офлайн-fallback на кешированный scoped-список; ошибка и повтор. Проверить после обновления service worker. |
| Печать, узкий экран и тёмная тема | Печать доступна, кнопки решений скрыты; числовые и новые колонки читаемы, на узком экране таблица прокручивается. |

После этапа 3 работа остановлена. Исправление времени руководителем и интерфейс истории относятся к отдельному этапу 4.
