# Review глобального usersAll после этапа 3

## Обнаруженная регрессия

До этапа 3 `user.initialFetch()` последовательно загружал текущего пользователя, разрешения и общий справочник usersAll. Этап 3 исключил последний шаг для department.manager:manage без calendar.all:read. Это меняло общий жизненный цикл приложения из-за потребностей одной страницы.

Часть компонентов вообще не загружает справочник самостоятельно, другие подгружают его только в административном режиме `target=all`. Например, чат мог показывать «Личный чат» вместо имени и пустой выбор участников; форма отпуска и имена авторов могли зависеть от того, посещал ли пользователь ранее страницу с дополнительной загрузкой.

## Найденные зависимости

## Внесённые исправления

1. В `src/stores/user.js` восстановлен ровно прежний безусловный `await userAllFetch()` после userFetch/permissionsFetch. Метод initialFetch теперь совпадает с HEAD до этапа 3. Нет новых проверок ролей, фильтрации или ограничений общего справочника; поведение остальных разделов не переписывалось.
2. В `src/services/timesheets.api.js` добавлен локальный запрос меток отделов для табеля через существующий referenceApi, тот же GET `/ref/employees/internal`, timeout 5000 мс. Старый reference.api.js на ошибке возвращал mock-данные, поэтому report не мог отличить недоступный справочник от настоящих отделов. Общий клиент со старым fallback не менялся, чтобы не затронуть остальные разделы.
3. В `src/stores/report.js` только административная ветка использует этот необязательный запрос. Promise.allSettled отделяет его ошибку от обязательного GET timesheets. При timeout/HTTP-ошибке/не-массиве нет меток отделов, но строки, статистика и возможности из backend остаются. Некорректные типы user_id/department пропускаются, чтобы сортировка названий не могла уничтожить корректную таблицу. Ожидание необязательных меток ограничено пятью секундами.
4. Актуализирован отчёт этапа 3: прежнее утверждение об отключённом глобальном usersAll больше не действует.

## Безопасность списка табелей сохранена

- `allUsersData` заполняется исключительно результатом `getTimesheets(year, month)` — защищённого GET `/v1/timesheets/:year/:month` через прежний proxy `/apitime`.
- Не происходит обхода usersAll с созданием строк, индивидуальных запросов статистики для его пользователей или fallback на usersAll при ошибке timesheets.
- Наличие профиля в глобальном справочнике не предоставляет ни просмотра времени, ни редактирования, ни согласования. Маршруты и permissions не менялись.
- Действия по-прежнему зависят от canApprove, ожидаемой ревизии и серверной проверки. Собственный табель руководителя не добавляется из usersAll.
- Общий ControlsCalendar в режиме report не делает дополнительный userAllFetch. Теперь глобальный справочник штатно загружается приложением для общих разделов; это не источник доступных табелей.
- При отказе обязательного GET timesheets строки очищаются и показана ошибка, а не данные других пользователей.

## Административная таблица при сбое APIREF

По исходникам: значения allUsersData и loadedPeriod получаются из успешного timesheets независимо от результата запроса меток. При отклонённом запросе APIREF departmentMap/departments остаются пустыми. Некорректное тело также не создаёт метки. В ReportTable скрывается селектор отделов и выводится плоский список, без вымышленных отделов.

Существующий watcher страницы после окончания загрузки сбрасывает выбранный отдел в all, если его больше нет. Поэтому прежний выбранный отдел не скрывает всю таблицу после сбоя справочника. Фильтр статусов, сводка, цифры, ссылки администратора и печать не менялись. При наличии валидных меток обычная группировка/фильтрация сохраняются.

Это проверка веток кода; реальный timeout, сбой APIREF и браузерное отображение не исполнялись.

## Ручная проверка

1. Войти руководителем без calendar.all:read сразу в чаты: проверить штатный GET users/timetrack при инициализации, имена/поиск собеседников, выбор участников и подписи авторов.
2. Перейти в отпуска, календарь, собственную карточку и доступные настройки/чеки: проверить прежние имена, списки выбора и дни рождения без необходимости предварительно заходить на другую страницу.
3. Открыть report: строки должны соответствовать исключительно GET timesheets. Пользователи другого отдела, присутствующие в usersAll, не должны появиться в таблице. Отказ timesheets не должен включать fallback.
4. У администратора проверить прежние числа/фильтры/ссылки/печать. Затем выбрать конкретный отдел и заблокировать запрос `/apiref/ref/employees/internal`, оставив timesheets доступным: после перезагрузки (не позднее timeout меток) таблица остаётся, отдел сбрасывается на all, статусный фильтр работает.
5. Повторить APIREF HTTP 503, timeout, HTML и JSON с неверным типом department; не должны появиться mock-отделы или ошибка основной таблицы. Восстановить APIREF и проверить возврат меток.
6. Руководитель без canApprove не получает действий; подмена frontend-состояния и прямой запрос чужого табеля по-прежнему проверяются backend. Собственный табель не появляется из глобального справочника.

Backend, API-контракты, SQL и бизнес-логика подтверждения не изменены. Этап 4 не начат.
