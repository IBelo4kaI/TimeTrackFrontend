# Проверка подтверждения группового автосохранения

## Границы проверки и причина

Изучена цепочка `DayEditor → runGroup → createUpdatesObjects → calendar.updateDay → HTTP → initialFetch → syncGroupDays → same`. Backend прочитан для проверки контракта, не изменён.

Подтверждён дефект по исходникам: при смене нерабочего типа на `work` без отдельного выбора места `groupTarget` оставлял `workLocation: null`. Helper отправлял null, backend (`internal/user_time_entry/helper.go`, `normalizeWorkLocation`) сохраняет `office`. Ответ календаря содержит `office`. Сравнение всего объекта через JSON.stringify считало `null !== office` ошибкой даже при успешном сохранении. Для нерабочих типов backend, напротив, очищает место работы, а календарь возвращает пустую строку вместо SQL NULL.

Дополнительное расхождение контракта: `hours_worked` хранится в MySQL как DECIMAL(5,2); календарь возвращает JSON number через float32. Сравнение исходного ввода, например 7.333, с сохранённым 7.33 давало ложную ошибку. Число дней само по себе не участвует в проверке.

**Конкретный случай пользователя с 9 днями не воспроизводился на работающем API.** Его точную первопричину без исходных значений и ответа календаря подтвердить нельзя. Устранены установленные по исходникам механизмы ложного отрицания; успешная сборка не подтверждает исправление конкретного серверного случая.

## Исправления

- Единое сравнение отдельных полей без JSON.stringify для подтверждения одиночных и групповых записей. Часы сравниваются численно с точностью хранилища; отсутствующие/пустые часы не приравниваются к нулю. Для nullable-строк календаря пустая строка, undefined и null нормализуются в отсутствие значения.
- Ожидание группы учитывает контракт места работы: рабочий день без места получает office, остальные типы — null. После формирования запроса через существующий helper ожидание строится из реально отправленных полей, включая запрет изменения типа у защищённых дней.
- У существующих записей проверяются изменяемые поля; после отправки также проверяется обязательная нормализация места работы. У новых — все три поля и наличие userTimeId; у удалённых — отсутствие userTimeId. Несовпадение заданных часов/типа/места не признаётся успехом.
- План исключает уже совпадающие дни. При неопределённом результате сохраняются ожидания отправленного пакета, включая поля создания и побочные изменения. До повторной записи выполняется существующее перечитывание сервера. Подтверждённые дни пропускаются, оставшиеся отправляются как create/update согласно актуальному наличию записи. Не затронутые ожиданием поля берутся из свежего календаря.
- Изменения draft во время запроса сохраняются и учитываются следующей итерацией. При ошибке ожидания и пользовательский ввод остаются; после полной сверки очищаются ошибка и ожидающие изменения, показывается «Сохранено».
- Ошибка перечитывания не заменяется успешным подтверждением; смена сотрудника/месяца после запроса также прерывает сверку.

## Диагностика

Только при неудачной сверке в development-сборке выводится `DayEditor: group confirmation failed`: дата, create/update/delete, проверяемые ожидаемые и фактические значения и причины `missing_day`, `missing_entry`, `entry_still_exists`, `mismatch:<поле>`. Тип выводится системным именем вместо UUID. ФИО, userId, комментарий, токены и HTTP-объекты не выводятся. В production подробный вывод отключён. Клиент получает короткое сообщение «Не удалось подтвердить изменения. Повторите проверку.»

Для подтверждения причины конкретного инцидента нужен этот диагностический объект из development-сборки для первой проблемной даты. Не следует присылать полный ответ календаря с персональными данными.

## Проверено по исходникам / ручные сценарии

Проверки ниже прослежены по коду, но не исполнены с реальным API. Новые автоматизированные тесты и dev-сервер не создавались.

1. Выбрать 9 дней, изменить часы: запросы включают только несовпадающие записи; после сверки — «Сохранено».
2. Изменить только часы в группе с разными типами и местами: остальные поля остаются индивидуальными, типы защищённых дней не меняются.
3. Изменить только место: меняются доступные рабочие дни; нерабочие и пустые даты не создаются из-за выбора места.
4. Изменить только тип на work из нерабочих дней: ожидается office при отсутствии места; обратная смена очищает место. Проверить null/пустую строку из календаря.
5. Смешать новые и существующие записи: сначала обновления, затем создания; наличие id проверяется после записи. Если для новых дней не выбран тип, остаётся прежняя валидация.
6. Проверить часы 7, 7.30 и 7.333: сохраняемая точность — 2 знака. Пустое/нечисловое значение не считается корректно сохранённым нулём.
7. Имитировать частичное применение пакета или потерю ответа: повторная проверка сначала читает сервер; совпавшие записи не отправляются повторно. Отдельно проверить частично созданные записи — повторный create не должен включать даты, уже имеющие id.
8. Имитировать HTTP 200 без изменения заданного поля: остаётся ошибка, выводится конкретное несовпадение. Для удаления существующий id также означает неподтверждённый результат.
9. После сбоя повторить проверку, когда сервер уже соответствует ожиданиям: без новых записей/событий истории, ошибка очищается.
10. Быстро менять часы во время запроса: существующая единая очередь и debounce сохранены; следующая итерация применяет последний draft.
11. Одиночный редактор: create/update/delete, повтор после сбоя, обязательный комментарий руководителя, закрытие с ожиданием flush. Его baseline/очередь не заменены, сверка использует то же семантическое сравнение.
12. Недоступность календаря после успешной записи: не показывать ложное «Сохранено», сохранить возможность безопасной повторной проверки.

Риск одновременной правки другими клиентами остаётся ограничением существующего API без условной ревизии для этих операций; новый протокол блокировок не вводился.
