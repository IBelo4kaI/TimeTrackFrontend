# Подтверждение табелей — этап 4

Реализованы frontend-правки рабочего времени руководителем и история дней в существующем календаре. Блокирующих несовместимостей backend не обнаружено. Backend, SQL, миграции, расчёты часов и глобальная инициализация usersAll не изменены.

## Интерфейс

- В таблице `/report` календарная ссылка доступна у каждой строки, которую вернул backend. Она открывает существующий `/calendar?id=...&year=...&month=...` на выбранном месяце. Административные карточки сотрудников по-прежнему доступны только с прежним calendar.all:read.
- Календарный route использует существующий departmentManagerAccess. Наличие query ID в usersAll не считается разрешением: выбранный ID запрашивается у backend, даже если профиль отсутствует в общем справочнике. Смена query сотрудника/месяца также перезагружает календарь.
- Над календарём показаны сотрудник, месяц и полученное состояние подтверждения. После реальной правки approved-месяца отображается needs_review и пояснение о повторном подтверждении. При ошибке запроса показывается недоступность статуса, а не выдуманный pending.
- Двойной клик по дню на desktop, нажатие дня на mobile и существующая кнопка добавления используют прежнюю универсальную форму. Для scoped-правки руководителя доступны только work, часы и офис/удалённо; добавлена обязательная причина. Контекстное/мобильное быстрое действие руководителя тоже открывает эту форму, не отправляет изменение без причины.
- При недопустимом дне руководитель получает пояснение: нерабочий тип, кадровое/системное происхождение либо отсутствие подтверждённого доступа/истории. Удаление разрешённой work-записи требует той же причины. Валидация удаления сделана в обработчике, поскольку общий modal.deleteAction не вызывает submit-валидатор.
- У каждого дня с историей есть кнопка «История изменений». После финального review подпись зависит от последнего события даты: «Изменено руководителем», если оно manager; «Есть изменения руководителя», если manager-событие было ранее. Вся история остаётся доступной. Кнопки есть в обоих существующих представлениях календаря; они не запускают выделение, редактирование или двойной клик родительского дня.
- По нажатию открывается существующий универсальный modal с историей дня: создание/изменение/удаление, значения до/после (тип, часы, место), автор и тип действия, дата/время, причина. Комментарии отображаются текстом, без HTML. Недоступное ФИО заменяется ID автора.

Пометка ищется по userId/дате в полной месячной истории, а не только по текущему entryId или последнему событию. Поэтому она сохраняется после дальнейшей правки сотрудником, удаления и пересоздания записи, а также после перезагрузки страницы. Дата без текущей записи остаётся днём календаря и позволяет прочитать историю удаления. Источник событий — только сервер; никаких локально придуманных отметок нет.

## Авторизация и запросы

При загрузке календаря дополнительно запрашиваются:

- GET `/v1/timesheets/:userId/:year/:month/history` — история и постоянные пометки.
- GET `/v1/timesheets/:userId/:year/:month` — состояние месяца.
- Для чужого календаря пользователя с manager-разрешением — существующий защищённый GET `/v1/timesheets/:year/:month`, чтобы получить строку и canEdit от backend.

Frontend-проверка разрешения выбирает маршрут запроса, но не выдаёт доступ. При scoped-операции нужны canEdit из серверного списка, успешно загруженная история, совпадение целевого сотрудника и загруженного месяца, разрешённый тип/provenance дня. Backend заново проверяет сессию, назначение и APIREF при каждом запросе и остаётся основным механизмом защиты. Обычный пользователь не превращается в руководителя из-за query-параметра или глобального usersAll.

Если у вызывающего есть соответствующее административное calendar.all:create/edit/delete, сохраняется административная ветка конкретного действия. Собственный календарь всегда остаётся на прежнем пользовательском пути. Для scoped-действий используется только PUT `/v1/timesheets/:userId/:year/:month/entries` с operation, entities и непустым comment до 4000 Unicode-символов. actor_id/actor_type и их camelCase-аналоги не передаются.

UI проверяет старый тип: руководитель не может заменить или удалить vacation/medical/decree/time-off/другую нерабочую запись. Дополнительно повторяется доступная из истории проверка текущего entryId на system-автора или источник vacation/sick_leave. Это подсказка и ранний отказ, а не замена серверной проверки. Управление общими calendar_events не добавлялось.

Отказ в истории не скрывает весь обычный календарь: показывается сообщение и кнопка обновления. Scoped-редактирование при этом закрыто. При отказе основного calendar-запроса данные очищаются. При переключении месяца/сотрудника старая история, canEdit и состояние очищаются; старый ответ не заменяет новый из-за существующего счётчика загрузок.

Для календаря добавлен NetworkOnly в существующий PWA-кеш, как уже для timesheets: защищённые календарные данные не подставляются из офлайн-кеша при отказе backend/APIREF или другой сессии. Это означает, что офлайн-fallback для calendar больше не используется; редактирование в любом случае требует сервера.

## Сохранение и обновление

После PUT календарь, статистика, история, canEdit и состояние месяца перезагружаются. До серверного ответа локальный approved/needs_review не присваивается. После отказа PUT также выполняется обновление текущего календаря, чтобы пересмотреть изменившийся scope или защищённые записи. Ошибка остаётся в форме и в уведомлении; операция не объявляется успешной.

Форма фиксирует сотрудника, месяц и выбранные дни при открытии. При смене контекста перед отправкой требуется открыть форму заново. Запрос руководителя фиксирует ID/месяц до await, не применяет ответ к другому календарю и блокирует параллельную scoped-запись из этой страницы.

Контракт backend допускает один operation на PUT. Для руководителя смешанный набор новых и уже существующих дней отклоняется до отправки с просьбой выбрать их отдельно. Однородные батчи сохраняются одним запросом. Это устраняет риск частичного успеха двух отдельных manager-запросов. Прежние смешанные пользовательские/административные батчи не переписаны.

Табель `/report` при возвращении загружает свежий список и статусы через свой существующий onMounted. Его фильтры, сводка, административные ссылки, печать и действия подтверждения не менялись, кроме появления календарной ссылки у руководителя.

## Совместимость, проверенная по исходникам

- В updateDay/deleteDay legacy-ветки используют те же create/update/deleteUserTimeEntry и прежние тела без нового обязательного поля. У сотрудника для собственного времени и у администратора с соответствующим all-правом причина не стала обязательной.
- `src/services/userTimeEntries.api.js` не менялся. Создание payload и сохранение места работы в `src/helpers/usertimeentry.helpers.js` остались прежними; финальный review добавил в clearDays только фиксацию владельца/месяца и защиту второй фазы от смены контекста. Для обычного/административного отпускного дня clearDays по-прежнему обнуляет часы вместо удаления vacation; manager-путь это действие не получает.
- Блок вычислений calendar.js от workingHours до финального return сравнен с HEAD: совпадает. `src/utils/plannedHours.utils.js` не изменялся. Пересчёт статистики идёт прежним GetStatistics, формулы не заменены.
- Кадровые frontend-модули отпусков, больничных и их API не менялись. Их данные в календаре доступны истории, но не стали разрешёнными для scoped-редактирования.
- Глобальный user.initialFetch и загрузка usersAll, восстановленные после review, не менялись. Общий справочник используется для подписей профилей, а не для выдачи canEdit или списка доступных табелей.

Это проверки исходников, а не результаты живого HTTP/SQL-прогона.

## Сценарии ручной проверки — требуют окружения

1. Руководитель открывает сотрудника из report: календарь того же месяца, корректное ФИО/ID и состояние. Повторить переход по query на другого сотрудника без полной перезагрузки.
2. Сотрудник другого отдела, отсутствие назначения и отозванное manager-право: backend закрывает чтение/PUT; нет старой истории/строк предыдущего сотрудника. Самостоятельная подмена query не даёт доступ.
3. Новая work-запись: существующая форма, work выбран по умолчанию, office/remote и часы, обязательная причина. В Network один PUT operation=create, без actor-полей. Проверить manager в истории.
4. Изменение work: PUT update, до/после отражают часы/локацию, статистика и статус обновлены.
5. Удаление work: пустая/пробельная причина не отправляет запрос, >4000 символов не допускается. Валидная причина → PUT delete, запись исчезает, история и пометка сохраняются на пустом дне.
6. Vacation/medical/decree/time-off и work с системным/кадровым provenance: UI объясняет запрет; прямой поддельный PUT всё равно должен быть запрещён backend. Смешанный work+защищённый день не должен частично измениться.
7. Manager-батч из нескольких новых дней и отдельно из нескольких work-записей: один запрос на операцию. Смешанные новые/существующие просят разделить выбор до запроса.
8. Правка утверждённого месяца: после фактического изменения needs_review и сообщение о повторной проверке; после no-op статус не сбрасывается сервером. Вернуться в report и проверить актуальные цифры/статус; подтвердить актуальную ревизию.
9. Сотрудник открывает собственный календарь: видит отметку и историю, включая старые manager-события после собственной последующей правки и после пересоздания дня. Собственное добавление work/medical, изменение, clear и отпускная очистка используют прежние endpoints без обязательной причины.
10. Администратор: прежние операции всех разрешённых типов, office/remote, смешанные батчи и очистка vacation остаются на старых маршрутах с прежними правами. Повторить с отдельными create/edit/delete-правами и с одновременной manager-ролью.
11. История дня: создание/изменение/удаление, корректные nullable author/entry ID, значения до/после, длинный многострочный комментарий, автор без профиля, системное событие. Комментарий с HTML должен оставаться текстом.
12. Mobile: нажатие дня и групповой выбор открывают ту же форму. История не запускает edit/selection. Desktop: история не выделяет день и не вызывает dblclick-редактор.
13. Быстрая смена месяца/ID во время загрузки и открытая форма при смене контекста: старые ответы не заменяют новый календарь, старая форма не пишет новому владельцу/месяцу.
14. Отказ history/status: обычный календарь остаётся, недоступность явно показана; manager-правка без истории заблокирована. Отказ основного календаря/APIREF не подменяется старым PWA-кешем.
15. Проверить сохранённые отпускные процессы, административную таблицу, фильтры и печать report после возврата из календаря; обновить service worker перед проверкой установленной PWA.
