# Финальный регрессионный аудит после этапа 4

Проверены текущие исходники frontend, diff с HEAD для прежних сценариев, исходная реализация этапа 4 и серверные проверки/аудит чтением. Backend, HTTP API-контракты, миграции и расчёты времени не изменялись. Последующие задачи не выполнялись.

## Результат и уровень доказательств

Обнаруженные ниже проблемы исправлены точечно. Production-сборка и проверка diff исполнены; сценарии с живыми сессиями, мобильным браузером и реальной БД не запускались. Вывод «проверено по исходникам» не означает выполненный HTTP/SQL-тест.

## Найденные проблемы и исправления

### 1. Мобильное одиночное выделение могло открыть неправильную дату

На mobile `selectDay` вызывает addItem, который сохраняет выбранный день в selectedItems, но не обязан заполнять selectionStart. Форма брала selectionStart при одном выбранном дне. При null или старом selectionStart могла открыться другая дата; parseDate(null) давал 1970 год, а scoped-запись затем отклонялась.

Форма теперь берёт единственный день из фактического selectedItems. Наличие кнопки удаления тоже определяется открытым снимком editedDays, а не чужим selectionStart. Для сотрудников/администраторов это исправляет тот же общий путь формы, не меняя payload или разрешения.

Файл: `src/stores/addReportModal.js`.

### 2. Частично успешный административный батч оставлял устаревший календарь

Legacy updateDay отправляет update и create отдельными запросами. Если update прошёл, а create завершился ошибкой, прежнее обновление календаря после обоих await не выполнялось. На экране оставались старые часы, история и подтверждение, хотя сервер уже изменил часть времени.

Перезагрузка исходного текущего контекста теперь находится в finally для legacy update/delete. Исходная ошибка продолжает передаваться форме, успех не выдумывается. Контракты, порядок update→create и возможность смешанного административного батча сохранены. Если пользователь уже перешёл в другой календарь, завершение старой операции не запускает лишнюю перезагрузку нового.

Файл: `src/stores/calendar.js`.

### 3. Очистка work+vacation могла продолжиться для другого сотрудника

clearDays сначала удаляет обычные записи, затем обнуляет часы vacation через update. Между фазами есть await, а прежняя вторая фаза снова читала изменяемый selectedUserId. При навигации во время первой фазы она могла сформировать запрос для нового сотрудника.

Владелец и месяц фиксируются в начале. Если контекст изменился, вторая фаза не отправляется: пользователь получает объяснение и должен открыть исходный месяц для проверки уже выполненного удаления. При неизменном контексте payload и поведение прежние: обычные записи удаляются, vacation остаётся и получает нулевые часы.

Файл: `src/helpers/usertimeentry.helpers.js`.

### 4. При смене сотрудника оставались прежние показатели

Дни/история/статус сбрасывались в начале загрузки, но statsData и individualStandards сохранялись до ответа. Панель могла временно показывать данные предыдущего сотрудника под новым именем. Теперь обе величины очищаются сразу; расчётные формулы не менялись.

Дополнительно загруженный набор данных привязан к ключу сотрудник+год+месяц. Проверяются и счётчик запросов, и этот ключ; scoped-правка требует соответствия загруженного контекста текущему. Старая история/canEdit не используется при смене контекста до новой загрузки. Флаг mutationPending освобождается даже при неожиданной ошибке повторной загрузки.

Файл: `src/stores/calendar.js`.

### 5. Уточнена подпись истории руководителя

Месячная история приходит от backend с ORDER BY id. После фильтрации по дате этот порядок сохраняется, поэтому последнее событие определяется по концу массива, без сравнения локальных часов и неоднозначных timestamp с одинаковой секундой.

| История даты | Пометка |
|---|---|
| Последнее событие manager | «Изменено руководителем» |
| Manager есть ранее, последнее employee/admin/system | «Есть изменения руководителя» |
| Manager-событий нет | «История изменений» |
| Истории нет | Нет кнопки истории |

История не сокращается до последних/manager-событий и не фильтруется по текущему entryId. После удаления, пересоздания или последующей правки сотрудником ранние события остаются. No-op, который backend не записывает как изменение, не меняет автора последнего события.

Файл: `src/components/Calendar/DayTimeHistoryButton.vue`. Общий компонент используется desktop и mobile.

### 6. Новые вспомогательные запросы не должны ждать бесконечно

Календарь ожидает историю, состояние и server canEdit вместе с основными данными. Для этих дополнительных запросов теперь задан клиентский timeout 10 секунд. Ошибка/timeout истории даёт явное сообщение и закрывает scoped-правку, но не выдаёт ложное право. Ошибка состояния даёт «Статус недоступен». Ошибка списка для canEdit оставляет scoped-редактор закрытым.

Дополнительный axios config для getTimesheets передаётся только календарём; обычный список report не получил нового тайм-лимита. Legacy calendar/statistics/user-time-entry API не менялись. HTTP-маршруты и тела запросов прежние.

Файлы: `src/services/timesheets.api.js`, `src/stores/calendar.js`.

### 7. Query ID должен оставаться одним сегментом URL

После этапа 4 календарь допускает запрос ID, отсутствующего в usersAll, с проверкой backend. Старый getCalendarDays вставлял этот ID в путь без экранирования. Значение из query с разделителями могло изменить структуру запроса вместо обращения к одному целевому владельцу.

Теперь userId кодируется encodeURIComponent в calendar.api.js, как уже в timesheet API. Для обычных UUID URL не меняется; маршруты, поля и права прежние. Backend остаётся проверкой права на владельца, frontend не выдаёт разрешение по наличию профиля.

Файл: `src/services/calendar.api.js`.

## Расчёты и контракты

Сравнением исходников подтверждено полное совпадение блока вычислений calendar.js от workingHours до финального return с HEAD. `plannedHours.utils.js` и legacy `userTimeEntries.api.js` не менялись. В helper изменения касаются только владельца/контекста двухфазной очистки; createUpdatesObjects и нормализация полей payload сохранены.

Подтверждение времени не вынесено из серверной транзакции. Не добавлены frontend-авторизация по одному признаку роли, вычисление новой ревизии, подстановка подтверждённого статуса или локальный журнал вместо серверного.

## Исполненные проверки

- `npm run build` — прошла production-сборка.
- `git diff --check` — пройдено.
- Локальное сравнение исходников расчётного блока, старого API и глобального user store с HEAD.

Новых автоматизированных тестов нет. Не запускались dev-серверы, браузерные сценарии с реальной сессией, live curl и SQL/миграции. Существующее предупреждение о chunks больше 500 kB осталось; разделение bundle не менялось.

## Ручные проверки — не выполнены

1. Обычный сотрудник: work/medical/нерабочие типы, создание, изменение, удаление и смешанные дни без причины. Проверить прежние запросы, статистику и историю.
2. Администратор: смешанный update+create с нерабочими типами; смоделировать успех update и ошибку create. Форма показывает ошибку, календарь и monthState отражают фактически сохранённую часть. Не ожидать транзакционного отката двух HTTP-запросов.
3. Очистка work+vacation: без навигации work удалён, vacation сохранён с нулевыми часами. Во время первого запроса сменить сотрудника/месяц: вторая фаза не должна записать данные новому владельцу.
4. Mobile: выбрать ровно один день через «Выбрать», открыть действие, убедиться, что дата взята из selectedItems, а не 1970/предыдущий день. Повторить удаление и работу с группой дней.
5. M → E → M: после первой правки M «Изменено руководителем», после E «Есть изменения руководителя», после следующей M снова «Изменено руководителем». Повторить с admin/system в качестве последнего автора.
6. M удаляет запись; E создаёт её заново и затем меняет: проверить сохранность всех событий разных entryId и правильную подпись. Нажатие пометки открывает полный журнал.
7. Scoped-правка work с пустой/пробельной/слишком длинной причиной не отправляется. Корректная причина сохраняется в серверном аудите. Прямой запрос к чужому отделу и попытка изменения medical/vacation/system должны отклоняться backend, даже при подмене frontend-состояния.
8. Approved → реальная правка → needs_review; no-op сохраняет approved. Проверить и обычный CRUD, и scoped PUT, и кадровое изменение. Вернуться в report и подтвердить актуальную revision; устаревшая должна дать 409.
9. Быстро менять id/month/year, включая открытое окно и незавершённый PUT. Не должно быть данных, истории или canEdit от предыдущего контекста; форма для старого контекста требует повторного открытия.
10. Замедлить/отключить дополнительные metadata-запросы: по timeout недоступность показана, обычный календарь не скрывается из-за этой ошибки, manager-правка закрыта. Сбой основного календаря не подменяется PWA-кешем.
11. С полными и частичными admin-правами, с manager-ролью и без неё проверить отдельные create/edit/delete, в том числе vacation-only clear с разрешённым admin edit.
12. Query id со слешем/специальными символами не должен менять маршрут запроса; валидный UUID другого отдела по-прежнему получает серверный отказ.
13. Проверить неизменность отпускных/больничных форм, общего usersAll, административных фильтров/печати табеля, тёмной темы и установленной PWA после обновления service worker.

## Оставшиеся риски

- Legacy смешанный батч и work+vacation clear состоят из нескольких HTTP-операций. Их нельзя сделать атомарными без изменения backend/контракта; уже выполненная первая фаза не откатывается при ошибке второй. Теперь UI обновляется и не продолжает очистку в другом контексте.
- Проверки actual scope, акторов, транзакций, перехода needs_review и конкурентных ревизий требуют живых auth/APIREF/MySQL. Сборка их не доказывает.
- Дополнительные metadata читаются отдельными запросами, не единым согласованным снимком. Параллельная чужая правка между ответами может потребовать обновления; PUT всё равно заново проверяется backend. Клиентский timeout может временно закрыть scoped-редактор при медленной сети — без выдачи доступа по умолчанию.
- Происхождение work-записей до введения серверного аудита нельзя восстановить из отсутствующей истории. UI использует доступные тип/журнал; основной guard остаётся серверным.
- Изменения URL, мобильные жесты, фактическое состояние PWA и отображение печати проверены по коду, не браузерным прогоном. Для получения нового cache-policy нужен актуальный service worker.
